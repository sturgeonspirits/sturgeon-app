# Pre-rollout audit — sturgeon-app

**Date:** 2026-04-25
**Scope:** Whole-app code review (auth, RLS, points, redemptions, Toast, QR check-in, events/leaderboards, missions, push, input validation, secrets, error handling).
**Method:** Static code-only analysis. No live URLs hit, no production data touched.

## Severity legend

| Severity | Meaning |
|---|---|
| **P0** | Ship-blocker. Customers can be cheated, data corrupted, or auth bypassed. Fix before broad rollout. |
| **P1** | Fix soon. Real risk under normal traffic — race conditions, weak rate limits, data hygiene. |
| **P2** | Nice to fix. Hygiene, dev-only exposure, minor input validation. |
| **INFO** | Design notes / recommended hardening — not a defect. |

## Executive summary

The app's auth, role enforcement, and RLS architecture are in reasonable shape. The biggest pre-rollout risks cluster in three places:

1. **Concurrency/idempotency around points.** Most points-mutating endpoints follow a "read-then-write" pattern with no transactional or atomic guard. Combined with a `mission_completions` unique constraint that doesn't actually prevent duplicates and a `sync_points_ledger` trigger that silently clamps balances to zero, a fast attacker (or just an unlucky double-tap) can over-redeem and double-collect mission points.
2. **A `profiles: staff read` RLS policy that queries `profiles` recursively.** This is the canonical Supabase footgun and can either silently fail under load or open a wider read than intended. Several other policies copy the pattern.
3. **A handful of pointed risks:** `/api/dev-auth` exists in production code (gated only by `NODE_ENV`), `/api/staff/customer-search` interpolates user input directly into a PostgREST `.or()` filter, and `/api/journal-entry` has no rate limit, making points-farming trivial.

There are also **8 pre-existing TypeScript errors** the build is suppressing (see `npm run type-check`). They aren't all defects but they mean type safety isn't actually catching anything in those files.

**Recommended sequence:** fix all P0 items before rollout. P1s can be addressed in the first 1–2 weeks. P2s can be batched.

## P0 — Ship-blockers

### P0-1 — Recursive RLS on `profiles` (and copies on other tables)

**Files:** `supabase/migrations/20260320152559_remote_schema.sql:1100-1102` (and the same EXISTS-on-profiles pattern at lines 976, 1003, 1023, 1036, 1056, 1083, 1099, 1116, 1129, 1149)

```sql
CREATE POLICY "profiles: staff read" ON "public"."profiles" FOR SELECT
USING (EXISTS (SELECT 1 FROM "public"."profiles" "p"
        WHERE "p"."id" = "auth"."uid"() AND "p"."role" = ANY (ARRAY['staff','admin'])));
```

The `USING` clause queries `profiles` to decide whether the calling user is staff — but `profiles` itself has RLS enabled, so the inner `SELECT` re-evaluates the same policy. Supabase explicitly warns against this pattern: it can recurse, hit the planner, or simply return wrong results under concurrency.

**Fix:** create a `SECURITY DEFINER` helper that bypasses RLS:

```sql
CREATE OR REPLACE FUNCTION public.is_staff(uid uuid)
RETURNS boolean LANGUAGE sql STABLE SECURITY DEFINER AS $$
  SELECT role IN ('staff','admin') FROM public.profiles WHERE id = uid
$$;

-- Then in every staff-read/staff-write policy:
USING ( public.is_staff(auth.uid()) )
```

Update **every** policy that uses the recursive `EXISTS … FROM profiles` pattern: `earn_events`, `mission_completions`, `points_ledger`, `qr_tokens`, `reward_redemptions`, `spirits`, `leaderboard_events`, `leaderboard_team_members`, `leaderboard_teams`, plus the `profiles` policy itself.

### P0-2 — `mission_completions` unique constraint is broken

**Files:** `supabase/migrations/20260320152559_remote_schema.sql:623-624`, exploited via `lib/earn-events.ts:155-205`

```sql
ALTER TABLE mission_completions
  ADD CONSTRAINT mission_completions_user_id_mission_id_completed_at_key
  UNIQUE (user_id, mission_id, completed_at);
```

`completed_at` defaults to `now()` so every insert gets a unique timestamp. This constraint **never fires**. `lib/earn-events.ts:169-178` does a read-then-insert duplicate check that races: two parallel calls both pass the check and both insert.

Affected callers:
- `/api/qr-validate` (a single 15-min QR token can be replayed for double points)
- `/api/staff/complete-mission`
- `/api/staff/approve-mission-request`
- `/api/staff/finalize-night` (win mission)
- `/api/staff/leaderboard-score` (participation + win missions)

**Fix:**

```sql
DROP INDEX IF EXISTS mission_completions_user_id_mission_id_completed_at_key;

CREATE UNIQUE INDEX mission_completions_one_per_user_mission_when_not_repeatable
  ON mission_completions (user_id, mission_id)
  WHERE NOT EXISTS (
    SELECT 1 FROM missions m WHERE m.id = mission_completions.mission_id AND m.is_repeatable
  );
-- Postgres can't reference another table in a WHERE — use a generated column or
-- materialize is_repeatable on mission_completions, or simpler:
CREATE UNIQUE INDEX mission_completions_one_per_user_mission
  ON mission_completions (user_id, mission_id);
-- and store repeatable completions in a separate table, OR keep the
-- existing table and let the constraint cover only non-repeatable missions
-- by storing a `repeat_seq` integer that increments per repeat.
```

Recommended pragmatic fix: add `repeat_seq integer NOT NULL DEFAULT 1`, make `(user_id, mission_id, repeat_seq)` unique, and have the app increment `repeat_seq` on inserts for repeatable missions. For non-repeatable, `repeat_seq` stays 1, so a duplicate insert raises a constraint violation atomically — no read-then-write race.

### P0-3 — `sync_points_ledger` silently clamps balance to zero

**File:** `supabase/migrations/20260320152559_remote_schema.sql:131-150`

```sql
ON CONFLICT (user_id) DO UPDATE SET
  balance = GREATEST(0, points_ledger.balance + NEW.points_delta),
```

If a customer has 100 points and a -200 earn_event arrives, balance goes to `0`, not `-100`. Combined with the redemption races below, this makes **silent over-redemption** the default behavior: the redemption succeeds, the second redemption "looks like" it succeeds because the balance check passes (balance was 100, second redemption requires 100, both get approved before the trigger fires), and the trigger silently swallows the deficit.

**Fix:** make the trigger raise on insufficient balance instead of clamping. Move the check into the trigger so it's atomic with the insert:

```sql
CREATE OR REPLACE FUNCTION public.sync_points_ledger() RETURNS trigger
LANGUAGE plpgsql SECURITY DEFINER AS $$
DECLARE
  v_current integer;
BEGIN
  SELECT balance INTO v_current FROM public.points_ledger WHERE user_id = NEW.user_id FOR UPDATE;
  IF v_current IS NULL THEN v_current := 0; END IF;

  IF NEW.points_delta < 0 AND v_current + NEW.points_delta < 0 THEN
    RAISE EXCEPTION 'Insufficient balance: have %, need %', v_current, ABS(NEW.points_delta)
      USING ERRCODE = 'check_violation';
  END IF;

  INSERT INTO public.points_ledger ...
    -- (drop the GREATEST clamp now that the check is up-front)
END;
$$;
```

This turns every silent over-redemption into a 500 the API has to handle — much better than silent corruption.

### P0-4 — Redemption races: `/api/staff/redeem` Mode 1 and Mode 2

**File:** `app/api/staff/redeem/route.ts:36-67` (Mode 1), `:78-133` (Mode 2)

Both modes do read-then-write on the redemption record:

- **Mode 1:** `SELECT … WHERE status = 'pending'` → `UPDATE status = 'redeemed'` → `emitEarnEvent`. Two staff members approving simultaneously both find it pending, both call `emitEarnEvent`. Points get deducted twice; only one row is updated.
- **Mode 2:** `SELECT balance` → check `balance >= cost` → `INSERT redemption` → `emitEarnEvent`. Two parallel direct redemptions read the same balance, both pass the check, both deduct.

Combined with **P0-3** (silent clamp), this is straightforward to exploit in the wild — staff training won't save you from accidental double-clicks.

**Fix:**
- Mode 1: do the UPDATE first as `UPDATE … SET status='redeemed', redeemed_by=staff WHERE id=X AND status='pending' RETURNING id`. If no row returned, abort. Only then call `emitEarnEvent`.
- Mode 2: wrap in a Postgres function (`spend_points(user_id, cost, …)`) that uses `FOR UPDATE` on `points_ledger` and inserts the redemption + earn_event atomically. Or rely on P0-3's trigger to fail the insert.

### P0-5 — `/api/staff/finalize-night` race + fragile dedupe

**File:** `app/api/staff/finalize-night/route.ts:50-61, 134-138`

The "already awarded" check uses `like('notes', '%placement bonus%')` (fragile string match) and the `is_finalized = true` flag is updated **after** all the point awards, so two staff hitting "Finalize" simultaneously both pass the check and both award bonuses. Combined with the broken mission unique constraint (P0-2), the win mission also fires twice for 1st and 2nd place.

**Fix:**
1. Update first, award second. Atomic flip:

```ts
const { data: flipped } = await supabase
  .from('leaderboard_periods')
  .update({ is_finalized: true })
  .eq('id', periodId)
  .eq('is_finalized', false)
  .select('id')
  .maybeSingle()

if (!flipped) {
  return NextResponse.json({ error: 'Already finalized' }, { status: 409 })
}
```

2. Drop the `notes ILIKE '%placement bonus%'` check entirely once `is_finalized` is the source of truth.

### P0-6 — `/api/dev-auth` is in production code, gated only by `NODE_ENV`

**File:** `app/api/dev-auth/route.ts:1-37`

Hits `supabase.auth.admin.generateLink()` for `info@sturgeonspirits.com` and immediately redirects through it, logging the caller in as that email. Only blocked when `process.env.NODE_ENV === 'production'`. If a preview/staging deploy or a misconfigured Netlify env doesn't set `NODE_ENV=production`, this route is a one-click admin login.

**Fix:** make it impossible in any deployed build:

```ts
if (process.env.NODE_ENV !== 'development') {
  return new Response('Not found', { status: 404 })
}
```

…or wrap the whole route in `if (process.env.NEXT_PUBLIC_ALLOW_DEV_AUTH === 'true')` and never set that env in any deployment. A `.env.example` audit confirms `NODE_ENV=development` is documented but not enforced.

### P0-7 — `/api/journal-entry` POST has no rate limit and no per-day cap

**File:** `app/api/journal-entry/route.ts:9-67`

Every POST awards +15 points. No rate limit, no per-day cap, and no content validation (empty entries are fine). A scripted client can earn 15 × N points/minute. A real customer could do this from a phone in 30 seconds.

**Fix:**

```ts
import { rateLimit, getClientIp } from '@/lib/rate-limit'
const { ok } = rateLimit(getClientIp(req), 'journal', 5, 3600)  // 5/hr per IP

// Plus a per-user-per-day point cap
const today = new Date(); today.setHours(0,0,0,0)
const { count } = await service.from('earn_events')
  .select('*', { count: 'exact', head: true })
  .eq('user_id', userId).eq('event_type', 'journal_entry')
  .gte('created_at', today.toISOString())

const pointsThisEntry = (count ?? 0) >= 3 ? 0 : 15  // 3 entries/day count for points
```

Also reject empty entries: require `(spirit_name || spirit_id) && (nose || palate || finish || overall_notes)`.

### P0-8 — `/api/staff/customer-search` filter injection

**File:** `app/api/staff/customer-search/route.ts:32`

```ts
.or(`display_name.ilike.%${q}%,email.ilike.%${q}%,full_name.ilike.%${q}%`)
```

`q` is user-supplied and goes raw into PostgREST's `or()` filter syntax. A staff user (this is staff-gated, so the impact is bounded) can pass `q=,role.eq.admin` to inject a parameter and reshape the query. This is staff-only so it's not a public RCE, but staff with limited trust shouldn't be able to pivot into broader queries.

**Fix:** strip filter-syntax characters before interpolating, or use `.ilike()` chained calls instead:

```ts
const safe = q.replace(/[,)(*]/g, '').slice(0, 50)
.or(`display_name.ilike.%${safe}%,email.ilike.%${safe}%,full_name.ilike.%${safe}%`)
```

## P1 — Fix soon

### P1-1 — In-memory rate limiter is per-worker on serverless

**File:** `lib/rate-limit.ts:1-72`

Rate limits live in a `Map` in process memory. On Netlify Functions / Lambda, every cold invocation gets a new process. The "5 redemptions per IP per 60s" effectively becomes "5 per IP per worker per 60s" — useless against any non-trivial abuser. The comment in the file acknowledges single-process assumption but Netlify isn't single-process.

**Fix:** move to Supabase. Create a `rate_limits(key text, window_start timestamptz, count int)` table and a Postgres function that increments+checks atomically. Or wire Upstash Redis (cheap, takes 20 minutes).

### P1-2 — `CHECKIN_SECRET` / `QR_HMAC_SECRET` falls back to a hard-coded dev value

**File:** `lib/checkin-token.ts:16-19`

```ts
const SECRET = () =>
  process.env.QR_HMAC_SECRET ??
  process.env.CHECKIN_SECRET ??
  'dev-checkin-secret-change-me'
```

`??` only catches `undefined`/`null`. If either env var is set to an empty string (`QR_HMAC_SECRET=""`), the empty string slips through `??` and becomes the secret. Daily check-in tokens are then HMAC'd with `''` — anyone can mint them. (A previously failed deploy that wiped the var to `""` while keeping the key would expose this.)

**Fix:**

```ts
const SECRET = () => {
  const s = process.env.QR_HMAC_SECRET || process.env.CHECKIN_SECRET
  if (!s || s.length < 32) {
    if (process.env.NODE_ENV === 'production') {
      throw new Error('QR_HMAC_SECRET not configured')
    }
    return 'dev-checkin-secret-change-me'
  }
  return s
}
```

Also: `lib/env.ts`'s `validateEnv()` already requires `QR_HMAC_SECRET`, so confirm `instrumentation.ts` actually calls it (I didn't see that file referenced — verify).

### P1-3 — `CRON_SECRET` is "recommended" not "required" and has empty-string bypass

**Files:** `lib/env.ts:38-42, 89`, `app/api/push/event-reminder/route.ts:21-24`

`CRON_SECRET` is in `RECOMMENDED` not `REQUIRED`, and `env.ts` defaults missing values to `''`. `/api/push/event-reminder` does:

```ts
if (secret !== process.env.CRON_SECRET) return 403
```

If `CRON_SECRET=''` (env present but empty) and the attacker sends `x-cron-secret: ''`, both compare equal and the route runs. Low likelihood but trivial to harden.

**Fix:** require `CRON_SECRET` (move to `REQUIRED` in env.ts) and reject empty/short values in the route:

```ts
const expected = process.env.CRON_SECRET
if (!expected || expected.length < 16 || secret !== expected) {
  return NextResponse.json({ error: 'Forbidden' }, { status: 403 })
}
```

Same change applies to `/api/sync-menu` (already guards with `Boolean(syncSecret) &&`, which is correct — copy that pattern).

### P1-4 — `reconcileToastToProfile` can double-correct under concurrent runs

**File:** `lib/earn-events.ts:95-138`

Reads `target = MAX(toast_points)`, reads `prior = SUM(toast_import deltas)`, computes `delta = target - prior`, emits an earn_event tagged `toast_import`. If two `/api/staff/toast-sync` runs (or one staff sync + one `/api/auth/link-toast`) execute in parallel for the same user, both read the same `prior`, compute the same `delta`, both emit. Customer gets 2× the correction.

**Fix:** advisory lock per profile during reconcile:

```sql
SELECT pg_advisory_xact_lock(hashtext('toast_reconcile:' || profile_id));
```

…or a unique `(user_id, target_value, completed_at::date)` partial index on earn_events to make a duplicate emission fail.

### P1-5 — `/api/staff/customer/adjust-points` race

**File:** `app/api/staff/customer/adjust-points/route.ts:69-160`

Reads balance, validates resulting balance ≥ 0, emits earn_event. Two concurrent staff adjustments both see the same starting balance and both pass the negative check. With P0-3 fixed (atomic balance check in the trigger), this becomes safe. Keep it on the list as a verification target.

### P1-6 — `/api/sync-menu` clobbers all recipes before reinserting

**File:** `app/api/sync-menu/route.ts:150-161`

```ts
await supabase.from('recipes').update({ is_active: false }).neq('id', '00000000-...')
// then upserts the freshly-fetched batch
```

If the Google Sheets fetch returns a small number of rows (or the parser fails silently and `deduped` is empty), every recipe is deactivated. There's no "did we actually get any rows?" guard before clobbering.

**Fix:**

```ts
if (deduped.length < 5) {
  return NextResponse.json({ error: `Refusing to sync — only ${deduped.length} rows parsed` }, { status: 400 })
}
```

Adjust the threshold to whatever makes sense for your menu, but a non-zero floor protects against fetch-empty-payload accidents.

### P1-7 — `/api/staff/verify-otp` lacks app-level rate limit

Six-digit OTP = 1M codes. Supabase GoTrue rate-limits at the auth layer, but defense-in-depth at the app level for a staff-only endpoint is cheap. Add `rateLimit(ip, 'verify-otp', 5, 60)`.

## INFO — Design notes

### INFO-1 — Daily check-in token has a 48-hour validity window

Today's + yesterday's tokens both validate, intentionally, to handle midnight edge cases. A leaked token is good for ~48h. Acceptable for a bar use case but worth knowing.

### INFO-2 — Push subscriber data is leaked to staff but not to customers

The `push_subscriptions` table is RLS-gated to `auth.uid() = user_id` (own all). Staff send via service-role (bypasses RLS). No exposure issue — just noting that customers can read their own subscriptions if they need to surface a "manage notifications" UI later.

### INFO-3 — `validateEnv()` enforces presence but not strength

`lib/env.ts` checks that secrets exist but doesn't enforce minimum entropy. Consider rejecting secrets shorter than 32 chars / not hex.

### INFO-4 — No `Content-Security-Policy` headers

Didn't see `next.config.js` set CSP/X-Frame-Options. Worth adding before broad rollout — Lighthouse will flag it and it costs nothing.

### INFO-5 — No request body size limits at the edge

Most routes parse JSON without `req.text()` size guards. Next.js has implicit limits (1MB by default for the App Router) but worth confirming for `/api/staff/toast-sync` (which already explicitly checks 10MB) and for any other multipart uploads if added.

## What this audit didn't cover

- **Live load testing** — code-only audit by request. Recommend an actual load run against staging before rollout to catch slow queries (e.g., the unindexed `earn_events.context_id` filters in dedupe checks).
- **Mobile / PWA install paths** — service worker, manifest, offline behavior.
- **Email/OTP delivery reliability** under load.
- **Toast CSV format drift** — what happens if Toast adds/renames a column.
- **GDPR/CCPA delete flows** — `ON DELETE CASCADE` from `auth.users` looks correct but worth a dedicated pass.
- **Operational tooling** — logs, alerts, monitoring, on-call runbook. None of this is in the repo so I can't audit it.
